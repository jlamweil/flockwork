# LOOP — design search by hypothesis verification (2026-09-17, HQ/example-host-c)

Protocol: propose designs → extract their load-bearing hypotheses →
verify each for real (reproduce, test, or run — never cite where a test
is possible) → keep only verified designs. Notes appended as the loop
runs. Frozen-record discipline inherited: cite-or-refute, disclose all
discards.

## Designs on the table

- **D-B** (incumbent, VERDICTS §10): batcher substrate (flock/ledger/
  claim), git ref-CAS (C) only as fallback. Load-bearing hypotheses:
  H-B1 flock portability beyond HQ; H-B2 multi-host is genuinely out of
  scope for the swarm's actual needs; H-B3 the worker leg can be wired
  behind the spawn step without touching coordination code.
- **D-C** (challenger): git ref-CAS coordination as THE substrate
  (multi-host capable). Load-bearing hypotheses: H-C1 exactly-once
  cross-host under contention; H-C2 crash-revive semantics cross-host;
  H-C3 operational overhead acceptable vs single-host baseline.
- **D-HYBRID** (this loop's proposal): B for single-host production
  (proven), C for any cross-host lane — selected per-lane by transport,
  same claim/attempt/verdict row shape in the ledger either way.
  Load-bearing hypotheses: all of B's and C's, plus H-X1 (the two row
  shapes can be reconciled into one audit trail without a second
  coordination implementation).
