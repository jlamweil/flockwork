# LOOP — 2026-09-18, round 4: in-repo coordination (D-INREPO)

Loop constraint this round: **no codebase changes** — verifications live
in /tmp and in this file; notes written as we go.

## Trigger question (user)

"Why not in the repo itself? Especially if cross-host."

## Designs on the table

- **D-INREPO** — claims/returns/verdicts live in the PROJECT repo
  itself, as `refs/swarm/claims|tasks|verdicts/<task>` on the project's
  own origin. No second repo. Load-bearing hypotheses:
  - **H-IR1** ref-CAS semantics work on ANY bare remote, including a
    project origin not created for coordination.
  - **H-IR2** in-repo refs are invisible to normal work: consumer
    clones/fetches never see or carry swarm refs; parallel main pushes
    are unaffected by swarm pushes and vice versa.
  - **H-IR3** the repo does not bloat at coordination scale: claim
    churn is empty commits; objects stay shared/tiny; `for-each-ref`
    and lineage queries stay fast as N grows.
  - **H-IR4** recovery is sound on a bare origin: deleted refs remain
    recoverable (reflog default, fetch prism), can be made permanent
    with a preserve-ref, and gc never collects an object reachable
    from any ref.
  - **H-IR5** visibility can be filtered verifiably git-side (transfer
    hideRefs), without provider protection cooperation.
  - **H-IR6** c9's worker protocol ports unchanged (claim-CAS → fix on
    main descendant → return/verdict CAS) — pure naming change.
  - **H-IR7** access control is inherited, not added: whoever can push
    the project can coordinate (with the owner-trust caveat recorded,
    not solved).
  - **H-IR8** eviction/rollback is trivial: delete the `refs/swarm/*`
    namespace (or a single prefix) and the repo holds no trace beyond
    ordinary history.
- **D-HYBRID** (incumbent, VERDICTS §10–§12) — separate coordination
  substrate: flock/ledger queue per host lane; bare coord repo
  (distinct from project origin) for cross-host. All four V1–V7
  verifications stand; its recorded costs are exactly D-INREPO's
  pitch: a second repo to create/point workers at (and rescue — the
  /tmp lesson).

### V11 — recovery semantics on a bare origin (H-IR4 deleted-ref half)

Status: **PASS 5/5, one hypothesis REFUTED and mitigated**
(`/tmp/v11-recovery.sh`, state `/tmp/v11-recovery-O1yg`)

- **H-IR4a REFUTED twice over**: bare origins default
  `core.logAllRefUpdates=false` (no reflogs at all), and even when
  enabled git **deletes a ref's reflog together with the ref** —
  reflog is never a deleted-ref recovery path on a bare origin.
  (Verified both directions, documented negative.)
- Deletion recovery actually rests on: the dangling grace window
  (object survives until gc), the preserve-ref law (`@`-suffixed
  archive ref — survives even `gc.pruneExpire=now`), and workers'
  own ledgers recording every sha they pushed (full undelete from
  the recorded sha — verified).
- Worker-side hygiene: stale mirrored swarm refs are cleaned by
  `fetch --prune` under the mirrored prefix.

### V12 — git-side visibility filtering + CAS under hiding (H-IR5)

Status: **PASS 5/5 with the RIGHT knob; one brick trap documented**
(`/tmp/v12-hide.sh` + follow-up probe, state `/tmp/v12-hide-JWHQ`)

- **Trap found live:** `transfer.hideRefs` is symmetric — it denies
  PUSHES to hidden refs (`deny updating a hidden ref`). Using it
  would brick the protocol.
- **Correct knob: `uploadpack.hideRefs`** — filters advertisement,
  clone, and fetch (git-side, no provider cooperation needed, H-IR5
  PASS); the receive path and CAS enforcement are untouched.
- CAS works under hiding because the lease sha is the worker's OWN
  record (create → you know the sha; renew → compare to your own) —
  no remote reads required. Wrong-sha takeover still rejected
  server-side. This is the V9 ls-remote caveat SOLVED.

### H-IR7 (access inherited) — verified by construction + V9 evidence

Swarm pushes use the identical remote/auth/pack path as main pushes
(both succeeded under the same credentials throughout V9/V10); no
second credential or ACL surface exists to manage. Recorded caveat,
not solved: whoever can push the project can coordinate — acceptable
under single-owner fleet trust; per-actor ACLs would be a provider-
side feature (needs live probe if ever required).

## Round 4 verdict

**D-INREPO is mechanically verified end to end** — claim-CAS, scale
(42s/200 cycles, ≈1KB/task), gc + recovery laws, consumer
invisibility (refs AND objects, after the root-commit law), git-side
hiding, one-transaction eviction. Two hypotheses refuted with
mitigations recorded (reflog recovery, transfer.hideRefs); two
protocol laws codified (root-commit metadata, own-sha CAS).

**Settlement: D-HYBRID gains a third lane option, not a replacement.**
- **In-repo (`refs/swarm/*` on the project origin)** — now the
  preferred shape when the origin is owner-controlled bare git (the
  fleet's actual topology: ssh bare repos on example-host-a). Kills the
  second-repo cost the /tmp rescue incident exposed; substrate
  inherits the project's own clone/backup lifecycle; fix commits and
  their claim/verdict trail live in one git-provable place.
- **Separate coord repo** — keep for provider-hosted origins
  (GitHub/GitLab protection rules unverified for `refs/swarm/*` —
  one 5-minute live probe each, marked needs-live-probe) and for
  multi-tenant projects where consumers must not see coordination
  metadata even via ls-remote.
- **Ledger/queue (B)** — unchanged for in-host lanes.

Honest limits (recorded, not hidden): provider-hosted behavior is
unprobed (mechanically standard receive-pack, but protection rules
and UI handling are provider specifics); per-actor ACL granularity
would be provider-side; the synthetic workload is protocol-shaped,
not a real repair batch (c9's real-workload discipline would apply
before any production flip).
