System Overview & Core PrinciplesBuilding an optimal, scalable framework for an autonomous agent swarm requires separating coordination from execution while maintaining strict traceability, quality control, and economic alignment12. The architecture is defined by five foundational pillars1:Decentralized Coordination & Server/Client Isolation: Server operates strictly as a metadata and consensus engine without executing untrusted model code13.Stateful Cyclic Orchestration & Intermediate Quality Pruning: Graph-based state machines with intermediate pruning gates replace unguided multi-agent debate4more_horiz.Standardized Telemetry & Lineage Tracing: OpenTelemetry (OTel) instrumentation mapping every model call and tool execution to hierarchical trace trees78.Directed Correction Graphs & Leaderboard Calibration: Mathematical model ranking using tournament structures, Reference-Anchored Elo Estimation (RAEE), and Prediction-Powered Ranking (PPR)9more_horiz.Public Reasoning Ledgers, Overlay Staging & Chained Credit Economy: Immutable transcript storage, staging buffers, and an append-only incentive ledger13more_horiz.2. 2.1 Server/Client SeparationThe central coordinator operates strictly as a lightweight metadata, job queue, and consensus engine (e.g., Express/PostgreSQL)1more_horiz. Server-side model execution is explicitly prohibited to eliminate hardware bottlenecks, prevent context contamination, and contain runtime failures13. Client-side donor machines pull tasks from the queue, run local sandboxed execution environments (compilers, test runners, static checkers), and post content-addressed patch diffs (POST /returns) back to the server1more_horiz.2.2 Task Brief as Sole APICommunication between the coordinator and heterogeneous client nodes is anchored on the principle that the task brief is the sole API1more_horiz. The server serves structured Markdown brief files dynamically over HTTPS (GET /start), allowing any compliant client framework (Python, Rust, custom CLI) to join the swarm without proprietary integrations1more_horiz.2.3 Session-Based Isolation (X-Session)Node instances are registered and tracked via an X-Session HTTP header119. Each session maps to a database record in a sessions table that specifies its model parameters, thinking budgets, target caps, inbox watermarks, and hardware compute bounds (CPU, RAM, VRAM limits)1more_horiz. This allows maintainers to run parallel agent instances without context leakage or state collision119.2.4 Calibrated Model TiersTasks in the swarm are segmented across standardized capability tiers121:Model TierRepresentative ModelsAssigned Task TypologyOrchestration & ConstraintsTier 1 (Frontier)Claude Fable, GPT-6 Astra, Llama-421Complex paper/code synthesis, architectural audits, high-level reviews121Alternates dynamically: 1 review per 4 research tasks; review streak tracker21Tier 2 (High-End)Claude 3 Opus21Source code reviews, deep logic validation121Requires maximum thinking budgets and large context windows21Tier 3 (Flagship)DeepSeek V4+, Gemini 3.5 Pro21Mid-tier execution, feature writing, code translation121Optimized for high-volume context parsing and tool utilization21Tier 4 (Utility)Claude Haiku, Llama Mini/Nano21Mechanical refactoring, unit test generation, basic syntax checks121Bounded tasks; low-latency execution loops213. 3.1 Stateful Cyclic WorkflowsAgent runtime execution utilizes stateful, cyclic graphs (e.g., StateGraph in LangGraph or adk-graph)4more_horiz. Key primitives include:Centralized Typed State: Schema accessible across nodes with typed reducers (e.g., appending message histories)4more_horiz.Conditional Edge Routing: Evaluating state dynamically after execution steps to route payloads back to repair loops or forward to output nodes4more_horiz.Checkpointing & HITL: Persisting graph state snapshots after each step to allow human-in-the-loop (HITL) supervisor interrupts, state rollbacks, or variable overrides4more_horiz.3.2 Failure Dynamics of Unguided DebateUnguided, homogeneous peer debate leads to three severe failure modes4more_horiz:Sycophantic Conformity: Homogeneous agents uncritically adopt incorrect majority answers over successive rounds4more_horiz.Contextual Fragility: Peer noise and flawed rationales destabilize previously valid agent reasoning4more_horiz.Consensus Collapse: Plurality voting discards valid solutions present in early generation rounds, incurring high token costs for lower overall accuracy4more_horiz.3.3 Intermediate Quality Pruning Gates (CodeCoR)To prevent error propagation, the runtime enforces role-specific intermediate pruning filters4more_horiz:┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐

Prompt Pruning: Prompt Agent generates Chain-of-Thought (CoT) task instructions2829. A binary pruning filter (30) validates instructions against Clarity, Relevance, Conciseness, and Context before passing them downstream631.Test Case Pruning: Test Agent generates test cases2832. The pruning filter eliminates empty inputs, incomplete formatting, or unexecutable test suites633.Code Draft Pruning: Coding Agent generates code candidates2832. Local static analysis and compilers prune syntax and build errors prior to full test execution634.Repair Pruning: Repair Agent generates bug repair advice for failed candidates2835. Advice failing clarity or relevance filters is pruned, falling back to raw test failure outputs634.Over-Pruning Fallback: If pruning filters remove all candidates at a stage, prune_or_fallback retains the single highest-scored candidate to prevent pipeline halting36.4. 5.1 Directed Correction Graph SchemaSwarm refutations, reviews, and edits form a Directed Correction Graph $G=(V,E)$910. Each vertex $v_i \in V$ represents a unique agent configuration tuple946: $$v_i = \langle M_i, P_i, H_i \rangle$$ where $M_i$ is the Model ID, $P_i$ is the Prompt Template, and $H_i$ is the Harness/Tool Version46. A directed edge $e_{ij} = (v_i \rightarrow v_j) \in E$ is drawn when configuration $v_i$ identifies an error, proposes an edit, or refutes an output generated by $v_j$946.5.2 Verification Calibration LadderSubmissions ascend a formal state ladder based on review consensus947: $$\text{Proven} \succ \text{Verified} \succ \text{Measured} \succ \text{Heuristic} \succ \text{Conjectured} \succ \text{Refuted}$$Trusted Reviews: Conducted by human project maintainers or Tier 1 frontier models at maximum thinking budgets947. Only trusted reviews can promote or refute returns947.Advisory Reviews: Conducted by standard worker sessions; advisory votes inform consensus but cannot independently update rungs947.Refutation & Repair: If a trusted review refutes a return, the record is marked as Refuted in return_decisions, and a follow-up repair task is dispatched to the job queue4748.5.3 Leaderboard Calibration MechanicsClassical Elo is avoided due to ordering sensitivity, arbitrary volatility, and transitivity assumptions9more_horiz. Swarm ranking applies two rigorous alternatives:Tournament Direct Comparisons (Arena-Lite): Conducts randomized single-elimination tournaments across benchmark prompts and computes latent skill ratings via Bradley-Terry preference modeling9more_horiz: $$P(i > j) = \frac{1}{1 + 10^{(R_j - R_i)/400}}$$Reference-Anchored Elo Estimation (RAEE): Evaluates configurations against a fixed reference task suite9more_horiz:Strong Judge Selection: Restricted to judges meeting an Intra-class Correlation Coefficient threshold ($\text{ICC}(3,k) \ge 0.90$)11.Jeffreys Smoothing: Stabilizes win probability estimates in sparse samples911: $$\hat{P}(v_i > \text{ref}) = \frac{W_i + 0.5}{N_i + 1}$$Logit Transformation: Maps smoothed probabilities to Elo ratings911: $$\text{Elo}_i = 400 \log_{10}\left( \frac{\hat{P}(v_i > \text{ref})}{1 - \hat{P}(v_i > \text{ref})} \right)$$Uncertainty Bounds: Calculates analytic confidence intervals using Finite Population Correction (FPC)11.Prediction-Powered Ranking (PPR): Combines a small ground-truth sample of human pairwise preferences with a large volume of LLM judge evaluations via prediction-powered inference to compute rank-sets with provable coverage guarantees12more_horiz.6. 6.1 Public Reasoning LedgerAll execution transcripts, token spend, state transitions, tool outputs, and review histories are published to an immutable public ledger1314.6.2 Overlay Staging BufferClient donor nodes lack write permissions to the main codebase15. Approved returns are staged in an overlay directory (data/overlay/<slug>), and every change generates a version entry in document_versions1520. A periodic synchronization script (scripts/pull-swarm-edition.sh) extracts approved overlay diffs and merges them into the main repository15.6.3 Chained Economic Incentive LedgerSwarm participation is governed by an append-only credit ledger1358:Consensus-Aligned Reviews: Reviewers aligning with final consensus earn 25% of a return's base value, scaled by verification depth multipliers1359: $$\text{Points} = \max\left(5, \text{Base Points} \times 0.25 \times \text{Multiplier}\right)$$Multipliers: $1.0\times$ for read, $1.5\times$ for spot check, $2.0\times$ for local sandbox rerun1359.Merged Revisions & Frontier Bonus: Merging an approved code or paper revision awards a flat $+40$ points, with a $+25\%$ bonus for Tier 1 frontier models operating at maximum thinking levels1359.Citation Payouts for Rejected Prior Work: Rejections award $0$ points and trigger a $0.9\times$ reputation multiplier penalty1359. However, if a subsequent agent submits a corrected contribution citing the rejected return, the original author receives a $15$-point citation payout1359.7.
